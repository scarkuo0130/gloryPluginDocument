# 相對位置版面比對技能（layout-compare）

把 render 跟參考圖（美術示意圖 / 設計稿）逐元件比對。**只比相對關係，不比像素**。

## 為什麼不用 pixel diff
參考圖通常是「美術示意」：尺寸不同、假資料不同（全 Bill16888）、字體不同。直接 pixel diff（pixelmatch / ImageMagick compare）會整片紅、無意義。我們要的是**相對位置與相對關係正確**。pixel diff 只適合「同一頁改版前後」的回歸測試（見最後一節）。

## 比對主流程：以「最大物件」為錨（核心方法）
**先找最大物件當量尺，所有其他物件都用它來量。** 固定 5 步：

1. **找最大物件**：先界定「**正在修改的標的物**」範圍（要比對的那個元件 / 區塊），**只在這個範圍內**找面積最大的視覺元件，當作這次比對的「1 單位量尺」。
   - ⚠ **不要把標的物外的東西算進來**：整頁背景、外層面板 UI、容器底圖都**不算**——它們不是這次要修的標的。
   - 例：標的物＝「排行榜列」→ 最大物件＝**整列背板 capsule**（不是排行榜面板的背景、也不是整個 app 畫面）。
   - 標的物換了，量尺就換：標的物＝「ID 卡」→ 量尺＝卡框；標的物＝「跑馬燈 chip」→ 量尺＝ chip 底板。
2. **相對大小**：用最大物件去量其他每個物件的大小（寬/高 ÷ 最大物件的寬/高，以 % 表示）。
   - ⚠ 兩件最常漏：① 物件可以**超過量尺**（例：獎牌高 = 背板 122%，凸出上下緣，這是正常設計，不要因為「比背板大」就以為錯）。② 每個物件還要查**自身寬高比 vs 它的原圖比例**（render ratio ≈ 原圖 ratio？差 >0.03 即變形）。注意原圖可能也有透明留白，naturalWidth/Height 才是真值。
   - 量到的「大小差很多」常是真問題（實例：獎牌只做到背板 50%，參考是 122%，肉眼一看就小一截）。
3. **相對位置**：用最大物件去量其他物件的位置（中心 x、中心 y 相對最大物件邊界的 %）。
4. **相對距離**：逐一量物件之間的間距（相鄰物件邊到邊距離 ÷ 最大物件寬，以 % 表示）。
5. **顏色**：逐一物件比顏色（render 用 computed color；參考圖肉眼/取色）。

> render 側用下方 snippet 取客觀值；參考圖側若有原圖檔，crop 該物件量像素換算 %（沒檔就讀圖估，並標「估」）。同單位（都對最大物件的 %）才能直接對齊。

> **量參考元件大小要乾淨，否則會抓錯數字**（實例：獎牌第一次量到 122~136%，是被緞帶尾/陰影/鄰列汙染；乾淨重量才知是 110%，我照 122% 做就把獎牌做太大）。可靠做法：① 限定**該列自己的 y 窗**，別讓上下鄰列混入；② 取**該物件獨佔的欄**（如獎牌取膠囊左緣外的純獎牌欄）；③ **低飽和物件（銀/銅/灰）像素偵測會偵不全**→ 拿同組高對比的那個（金）來量，或直接 crop 出來用 `Read` 目視量；④ 像素值和目視 crop **互相交叉驗證**，差太多就是某邊被汙染。

> **步驟優先序**：Step 4（相對距離/重疊）可**否決** Step 2/3 的調整。實例：Step 3 量到「分數偏右、該左移」，但左移後 Step 4 偵測到分數撞到名稱（gap 變負）→ 放棄左移。讀圖估的位置 %（如 cx）常因參考圖字較窄而低估，**碰到重疊一律以「不重疊」為準**。每次調完位置都要回跑 Step 4 的 gap 檢查（相鄰物件 edge-to-edge gap 必須 > 0）。

## 最大物件（量尺）本身的兩個陷阱 ⚠ 必查
量尺＝最大物件（通常是底板/背板圖），它自己若沒擺對，後面全部白量：

1. **素材透明留白會騙人**：PNG 常含透明邊（例：747×209 的背板，實際膠囊只有 663×129，上 34/下 46px 是透明）。若直接把整張 PNG 用 `width/height:100%` 塞進容器，**可視主體會被二次縮放變形**。
   - 先量素材**真實內容 bbox**（PIL `Image.getbbox()` 或 canvas 掃 alpha），算出可視主體的**真實比例**。
   - 把透明留白**裁掉**（PIL crop），或讓容器 `aspect-ratio` = 可視主體比例 + `object-fit` 不變形。
2. **不要硬拉變形**：`width:100%;height:100%` 會把圖拉成容器比例。實測：背板被拉成 ratio 6.8，參考是 ~5（差很多、肉眼可見變扁）。→ 容器 `aspect-ratio` 設成素材原圖比例，直接用原圖比例最安全。
3. **字體/固定 px 要用容器相對單位**：demo 欄寬常被 grid/flex 壓縮（如 660px 被壓到 455px），絕對 px 字體會相對變大而**重疊**。改用 `cqw`（容器 `container-type: inline-size`），全列等比縮放、寬度無關、永不重疊。

> 驗證量尺對不對：render 量到的「最大物件 ratio」要等於素材原圖（裁留白後）比例，也要對齊參考圖量到的比例。三者一致才往下比子元件。

## 改完之後要重比哪些？（重驗範圍規則）
**預設：改完一定要重比，且不能只比改過的那一個元件**——版面是相對的，動一個會連鎖推到別人（實例：放大「獎牌」→ 頭像/中段/名稱/分數被往右推 → 名稱與分數重疊。只回看獎牌就漏掉）。依改動類型分級：

1. **改到「最大物件（量尺）」**（裁留白、改 aspect、換底圖）→ **全量重比所有元件**。量尺一變，所有相對 % 全變，等於重來。
2. **改到某個子元件的大小/位置** → 重比「該元件 + 它的左右/上下鄰居（距離、重疊）+ 任何跟它同欄/同列對齊的元件」。
3. **不論改什麼，每次都要回跑這兩個全域便宜檢查**（必跑，成本低、最會被連鎖破壞）：
   - **Step 4 gap 掃描**：所有相鄰元件 edge-to-edge gap > 0（抓重疊）。
   - **邊界/對齊掃描**：同類元件跨列的 left/top 是否仍一致、有沒有新的溢出壓框。
4. **收尾前一定做一次全量重比**（7 維 × 全元件），確認沒有殘留 ripple。中間迭代可只做 2+3。

> 一句話：**局部改、全域驗**。局部調省時間，但全域 gap/對齊掃描每次都跑，最後再全量過一次。

## 總流程：PDCA（Check 的唯一合格證據＝圖片比對）
本技能以 PDCA 跑，**收尾 Check 一定要用「圖片 vs 圖片」當合格證據，數字不算數**：

- **Plan**：界定標的物 → 找最大物件當量尺 → **量「spec 本身」**取各元件目標值（5 步、相對量尺 %）。⚠ 量尺與目標都要量 spec，不要量到別張圖。
- **Do**：改 CSS（用數字/cqw 對齊目標，這只是手段）。
- **Check**：**把 render 成圖，高解析對 spec 做畫面比對**（render→裁同元件→放大 3x→Read，或對 spec 像素量測交叉）。**這關才是驗收**。數字通過 ≠ Check 通過。
- **Act**：沒過 → 回 Plan 修；過了 → 把這次踩到的新樣態**回寫本 skill**（標準化），讓下次不再犯。

> 每次宣稱「調完」前，必須先產出**對 spec 的高解析畫面比對證據**。只有數字＝未完成。

## 鐵則 0：一定要做「畫面 vs 畫面」比對，不能只比數字
computed 數字（getBoundingClientRect / cqw）對，**不代表畫面對**。陰影、字體 metrics、圓角、視覺重量、抗鋸齒這些數字抓不到。**收尾必做**：

1. 把自己的 HTML **render 成圖**（chrome `take_screenshot` 存檔）。
2. 跟參考圖**裁同一個元件/同一列**，用 PIL **縮到同寬**、上下並排存成一張圖。
3. 用 `Read` 讀那張並排圖，**目視逐元件比**（大小/位置/顏色/視覺重量）。
4. 並排時排除「刻意不做」的差異（如簡化版拿掉的副標/裝飾），只比共同元件。

> 範例腳本（同寬上下並排）：
> ```python
> from PIL import Image, ImageDraw
> mine=Image.open('mine.png').crop(BOX_MINE); ref=Image.open('ref.png').crop(BOX_REF)
> W=760; fit=lambda im:im.resize((W,int(im.size[1]*W/im.size[0])))
> m,r=fit(mine),fit(ref); out=Image.new('RGB',(W,m.size[1]+r.size[1]+48),(20,20,28))
> out.paste(m,(0,24)); out.paste(r,(0,m.size[1]+48)); out.save('cmp.png')
> ```
> 同寬並排才能直接看出「某元件比參考大/小」——這是純數字比對最容易漏的（實例：數字顯示頭像 h79%『看似合理』，並排才發現我的頭像明顯比參考大）。

## 核心鐵則
1. **render 側用客觀數據**：chrome-devtools `getBoundingClientRect`，全部換算成「相對容器的百分比」（不是絕對 px）。
2. **參考圖側用結構化讀圖**：用 `Read` 讀截圖，估每個元件的相對位置（佔容器幾 %）。
3. **逐元件過 7 維檢查表**（見下），任一維不符 → 列為 diff，自己修，不丟「對嗎」。
4. 漏抓 diff 多半是「沒逐項過清單」，不是工具問題 → 清單**強制走完**。

## 7 維比對維度（每個元件都要過）
對 render 與參考圖的「每一個視覺元件」逐項對：

| 維度 | 問什麼 | render 取值方式 |
|---|---|---|
| **1 排列順序** | 由左到右、由上到下的元件序列一致嗎 | 看 DOM / boundingRect 的 x、y 排序 |
| **2 錨定邊** | 貼左緣/置中/貼右緣/凸出邊外 | left%、right% 相對容器 |
| **3 相對大小** | 元件高 ÷ 容器高、元件間寬度比 | rect 寬高 ÷ 容器寬高 |
| **4 對齊** | 垂直置中？同欄跨列同 x？baseline 對齊？ | 比各列同類元件的 left%/top% |
| **5 壓框/重疊** | 有沒有壓到外框圓角、蓋到隔壁元件 | 比元件 rect 與容器邊界、與鄰元件 rect |
| **6 層級 z** | 誰在上面（徽章蓋背板、數字蓋獎牌…） | computed z-index / 視覺遮擋 |
| **7 留白** | 元件間距是否一致、是否過鬆/過擠 | 相鄰 rect 間距 ÷ 容器寬 |

> ⚠ 第 5「壓框」最常漏。獎牌/徽章這類「凸出元件」一定要確認是**凸出框外**還是**壓在框內圓角上**——兩者視覺差很多。

## 標準流程
1. **讀參考圖**：`Read` 參考圖，列出元件清單 + 各元件的相對位置估計（佔容器 x%~x%、y%~y%）。
2. **開 render**：chrome-devtools 開 `file://`，跑下方量測 snippet，輸出每個元件的相對 box（%）。
3. **建比對表**：一列一元件，欄位＝7 維 × (參考 / render / 判定)。
4. **截圖 + Read**：`take_screenshot` 後用 `Read` 讀圖，肉眼覆核「壓框/重疊/層級/留白」這幾個量測抓不到的。
5. **逐項判定**：任一不符 → 自己改 → 回 step 2 重量。全過才算通過。

## 量測 snippet（render 側，相對 % 輸出）
chrome-devtools `evaluate_script`，把每個元件換算成相對容器的百分比，方便跟讀圖估計對齊：

```js
() => {
  const CONTAINER = '.lbr';        // 改成要比的容器 selector
  const PARTS = {                   // 改成容器內各元件 selector
    medal: '.lbr-medal', rank: '.lbr-rank', av: '.lbr-av',
    title: '.lbr-title', name: '.lbr-name', score: '.lbr-score', crown: '.lbr-crown',
  };
  const c = document.querySelector(CONTAINER);
  const cb = c.getBoundingClientRect();
  const pct = (v, base) => Math.round(v / base * 1000) / 10;   // 一位小數 %
  const out = {};
  for (const [k, sel] of Object.entries(PARTS)) {
    const e = c.querySelector(sel); if (!e) { out[k] = null; continue; }
    const b = e.getBoundingClientRect();
    out[k] = {
      left: pct(b.left - cb.left, cb.width),
      right: pct(cb.right - b.right, cb.width),   // 距右緣 %（負值=凸出右邊外）
      top: pct(b.top - cb.top, cb.height),
      wPct: pct(b.width, cb.width),
      hPct: pct(b.height, cb.height),
      overflowLeftPx: Math.round(cb.left - b.left),  // 正值=凸出左框外（壓框檢查）
    };
  }
  return { containerPx: { w: Math.round(cb.width), h: Math.round(cb.height) }, parts: out };
}
```

判讀重點：
- `left` / `right`：錨定邊。`right` 負值或 `overflowLeftPx` 正值＝凸出框外（壓框檢查的關鍵）。
- `hPct`：元件高佔容器高，跟參考圖估計比（如頭像應佔列高 ~75%）。
- 同類元件跨列比 `left` / `top` → 對齊一致性。

## 輸出格式（給使用者）
- **已對齊** ✓ 清單
- **diff 清單**：表格（元件 / 維度 / 參考 / render / 修法）
- 區分 **真實 diff（要修）** vs **mock 差異（假資料/配色示意，可忽略）**

## 與既有流程的關係
- 本 skill 是「UI 收尾 6 步 checklist」裡 **step 5「逐區比對」** 的細化工具。
- 不取代截圖+Read 紀律；是在其上加「7 維逐元件」結構，避免漏項（如「獎牌壓框」）。

## （選用）pixel diff：只用於自身回歸
要防「自己改 A 卻弄壞 B」時，對**同內容的前後版本**存 baseline：
```bash
# ImageMagick（已可用）
magick compare -metric AE before.png after.png diff.png   # diff.png 標紅變化區
```
⚠ 不要拿來比美術稿（內容不同會整片紅）。
